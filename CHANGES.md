# chocosolver version 0.6.0, unreleased

* Major release with Clafer 0.6.0.
* `chocosolver --version` prints the version of the pom and the build date, which Maven fills in (`version.properties`, no longer written by hand): the day of the build, or `-Dbuild.date=YYYY-MM-DD`, which the Makefile passes for `SOURCE_DATE_EPOCH`.
* Two Maven modules (the parent `chocosolver-parent`, in the repository's root): `frontend/`, the artifact `clafer-frontend`, with no dependencies, and `solver/`, the artifact `chocosolver` as before, which depends on it. The CLI is `solver/target/chocosolver-0.6.0-jar-with-dependencies.jar`. `SourceSpan`, `Lexer`, `Token`, `TokenKind` and `Diagnostic` are in the frontend, `SourceSpan` now in `org.clafer.frontend`.
* The explicit IR (`org.clafer.frontend.Ir`): one tree of records for the rich and the core explicit model that Clafer 0.6.0 prints (`clafer -m clafer`, and `--core`), the core being the tree without rich nodes, whether a node is rich a property of its type (`Core.richNodes`). `ExplicitParser` reads either, temporal models included, into it, with the first line's options (`--core`, `--tl=N`) and the provenance comments (`// final, model.cfr:56:5`), and `ExplicitPrinter` prints it exactly as the compiler does, with or without those comments. The declarations and constraints keep the places they were written. The rich constructs are enumerations, temporal modifiers, initializers with their clocks (`=`, `:= each`, `:= together`), the multiplicity of a top-level abstract clafer, the anchors (`initially`, `finally`), the behavioral patterns and the transitions; the core has the temporal operators (`X`, `F`, `G`, `U`, `W`, `previous`, `once`, `historically`, `since`, `triggered`), and a nested abstract clafer's multiplicity. Both read `real` and `double` and double literals with their exponents (`1.2e2`). For all 444 rich and core explicit models of Clafer's positive tests, `print(parse(m))` is `m`, with and without the provenance comments, and the core models have no rich node (`ExplicitConformanceTest`).
* `ToAst` builds the `AstModel` from the explicit IR and resolves its names; it replaces the parser of the explicit form, which built the `AstModel` from the text. It reads the core explicit model: a nested abstract clafer's multiplicity is a constraint of its parent on `#this.A`, as the compiler gives it to chocosolver. For all 141 static core models of Clafer's positive tests with a Choco output, the core model gives the same instances as the `.js` (`ExplicitCoreTest`). `real` and `double` have a diagnostic, since no backend solves them.
* The quantifiers over a set without variables, `some x`, `no x`, `lone x`, `one x` and `all x`, are one node of the explicit IR, `QuantifiedSet` (was `AllOf`, for `all x` only), as Clafer 0.6.0 prints them; `ToAst` builds `Asts.some`, `none`, `lone` and `one`.
* `ToCore` lowers the rich explicit model to the core: a port of the Clafer compiler's lowering (`Intermediate/Core.hs`), pass by pass, with the provenance of each lowered construct at its position in the rich model. For all 222 rich models of Clafer's positive tests, `toCore` gives the core model, and it is the identity on the core models (`ToCoreTest`). chocosolver solves the static rich models (`chocosolver --file model.des.cfr`): `ToAst` lowers the enumerations, the initializers and the multiplicities of the top-level abstract clafers with it, and the 141 static rich models with a Choco output give the same instances as the `.js` (`ExplicitCoreTest`). The rich model and the `.js` round trip read as before.
* **For users of the Java API of 0.5.7 and 0.5.8:** `org.clafer.frontend.ExplicitParser.parse` returns the explicit IR now, not the `AstModel`. What it returned is `org.clafer.ast.ToAst.parse(source)`, whose `Result` has the same `model()`, `objectives()`, `assertions()` and `diagnostics()`; `SourceSpan` is `org.clafer.frontend.SourceSpan`, in the artifact `clafer-frontend`.
* A model that declares itself the core in its first line (`//# OPTIONS --explicit --core`) has no rich construct: each is an error at its position, as the compiler gives it, e.g., `2:1: The core has no enumeration: the model declares itself the core (--core)` (`Core.richInCore`), also in a temporal model. The Clafer compiler rejects the same models.
* An error in the initializer of a clafer, e.g., `:= 1` without a clock, is reported, and the clafer is read without it, so its name is still found: the error is no longer followed by `No clafer named ...` for each use of the clafer.
* The parser of the full Clafer language, the first step of a Java frontend (`ClaferParser`, with `ClaferLexer`, `Layout`, the tree `Syntax` and `SyntaxPrinter`). It reads a `.cfr` model as the compiler does: the compiler's tokens (its reserved words and its Latin-1 characters), its layout (indentation to blocks, with its rules) and its grammar (`clafer.cf`), temporal included. It reports all the errors, of the lexer, the layout and the parser, each at the compiler's position, and goes on at the next line at the same or a lower indentation, so that the tree has the rest. For all 702 models of Clafer's tests (223 positive models, their 446 rich and core explicit regressions, and 33 negative models), it gives the compiler's parse tree, as the compiler's `printTree` prints it, or rejects the model at the position of the compiler's error (`ClaferParserConformanceTest`, with the trees that Clafer's `test/print-parse-trees.sh` writes). Nothing uses it yet.
* The symbols of a model, the second step of the Java frontend (`Symbols`): a symbol per clafer, enumeration and literal, with its UID, its parent, its super, the type of its reference, its card and group card with the compiler's defaults, its temporal modifiers and the clock of its initializer, by the compiler's rules (the desugarer, `UIDs.hs`, the inheritance resolver with gsdlab/clafer#67, `analyzeModule`). It reports the compiler's errors of these, at its positions: a super that is missing, not abstract, ambiguous or a cycle, a reference's target that is missing or ambiguous, an improper nesting or redefinition, an unsatisfiable group card, and duplicate siblings. For the 215 positive models of Clafer's tests without imports, the symbols declare the clafers of the rich explicit model (`test/regression/*.des.cfr.reg`), in its order, and so do the 446 rich and core explicit models, read as models (`SymbolsConformanceTest`).
* A model in the full syntax whose constraints are explicit runs end to end (`ToIr`): its symbols and its constraints, objectives and assertions, give the explicit IR, which `ToCore` and `ToAst` take as before, so no Clafer compiler is needed for it. Layout instead of braces and the cards, group cards and references the symbols infer are left out; the compiler's constraints of a reference to a set expression (`-> Alice ++ Bob`, `-> int -- 0`), the quantified nested assertions, the constants of `-> 2.5` and the negative numbers are as the compiler gives them. Every rich and core explicit regression reads as itself (`ToIrConformanceTest`), and so does each of them rewritten without braces and without what the symbols infer, 84% of the cards and group cards (`FullSyntaxConformanceTest`); the compiler compiles the 446 rewrites to the same regressions. `ACCDemo_attributedFeatureModels`, rewritten by hand, solves as the compiler's Choco output of the original (`FullExplicitModelTest`).
* Name and type resolution, the third step of the Java frontend (`Resolver`): each constraint, objective, assertion, initial value, transition and set-expression reference is resolved as the compiler resolves it, through a port of its desugarer, its name and type resolvers and the root's rewrites (`ResolverName`, `ResolverType`, `ResolverRoot`). So an implicit `this` or `dref`, a name that is not a UID, `let`, `sum`, `parent` and the conjunction `[a b]` are resolved, and the errors are the compiler's messages at its positions, the first of each constraint. A model in the full syntax needs no Clafer compiler, except for imports. For the 215 positive models of Clafer's tests without imports, `ToIr` gives the rich explicit model of the compiler (`ResolverConformanceTest`), and on 243 models of Clafer's tests and documentation none differs from the compiler's.
* Scopes and imports, the fourth step of the Java frontend. `ToIr` gives the scopes of the explicit model as the compiler writes them to its scope file (`clafer -m clafer --meta-data`, `model.des.cfr-scope`; `Scopes.scopeFile()`): a port of the compiler's scope analysis (`SimpleScopeAnalyzer`, with the unused and the empty abstract clafers, `ScopeAnalysis`) on the resolved model, in the compiler's order, and the ranges of `--minint`, `--maxint` and `--decimal-digits`, the decimal scale and the longest string. `ToIr.read(path)` reads a model with the files it imports (`--import=FILE` in `//# OPTIONS`, `ModelFiles`) as the compiler does, for local files: relative to the importing file, each once, before the files that import it, with the options of all the files combined (`ModelOptions`), and with the compiler's errors: a missing file, an import that is not a `.cfr` file, an import cycle, and options that differ between the files or that an imported file cannot give. A diagnostic is shown in its file, at its line there (`Result.messages()`). A qualified name, `A\b`, is `b`, and its errors are at `b`. A static model's `--tl` is not in its explicit model, as in the compiler. For all 223 positive models of Clafer's tests, imports included, the scope file is the compiler's (`ScopeConformanceTest`, with `clafer` on the path), and check 4 holds on the 8 models with imports too.
* The compiler's checks of a whole model, in the Java frontend, in the compiler's order (`ModelChecks`): no clafer is named after a keyword; an explicit model writes the clock of each `:=`; a top-level abstract clafer with `:=` and no clock has the multiplicity `*`; `--check-duplicates` (`-c`); with `-f`, which `--explicit` implies, the names are UIDs; a per-instance `:=` of an abstract clafer has a value with at most one element; a model that declares itself the core (`--explicit --core`) has no rich construct; and `--check-afm`. The errors without a position, e.g., of the keywords, are given as the compiler gives them (`Result.errors()`). As in the compiler, `--explicit` also means `--ss=none`, so an explicit model's scope file has no analysis. Each check gives the compiler's first error on small models (`ModelChecksTest`), and the frontend no longer accepts a model of Clafer's tests that the compiler rejects.
* chocosolver compiles a `.cfr` file with the Java frontend, in the same JVM, without the Clafer compiler and without writing a `.js` file (`Frontend`): `ToIr`, `ToAst`, and the scopes of the explicit model's scope file, then the model's `.cfr-scope` file and the command line's options, as before. The REPL's `reload` compiles the `.cfr` file again (it read the old `.js` file). The Clafer compiler (`clafer -k -m choco`) compiles the model instead with `--haskell-frontend`, and when the Java frontend cannot take it: an import of a URL, imports with `--import-root`, `--public-imports` or `--import-base` (new options, passed on to the compiler), a `[choco| |]` escape, or a model that the Java frontend rejects and the compiler compiles, whose output is solved after the Java frontend's errors. A temporal model, or one with `real` or `double`, gets the Java frontend's diagnostic at each such construct. All 141 static positive models of Clafer's tests with a Choco output solve as their `.js` does, with the same scopes (`CfrConformanceTest`), and the negative models are rejected; `chocosolver --file model.cfr -n 5` gives the same output with and without `--haskell-frontend` on all 140 of them without an escape. The `.js` path and Rhino stay, for the fallback and `.js` files.
* The Clafer language server, `clafer-ls` (the module `lsp/`, the artifact `clafer-language-server`, on Eclipse LSP4J 0.24.0; `clafer-ls.jar` in the binary distribution and the images, with its launcher): JSON-RPC on stdio, a full analysis with the Java frontend on every edit of the open documents and their imports, which may be unsaved. It gives the errors at their UTF-16 characters, the outline, go to definition, find references, hover, completion of the names in scope (after a `.`, the children of the path) and rename. Rename refuses a name that is not a clafer name, a name already taken, and a clafer of a model with errors. The frontend records the clafer of each written name (`ToIr.Result.names()`, `Names`), which it is built on. On Clafer's positive models, go to definition at each of 3,106 names goes to the resolver's clafer, and renaming each of 2,091 clafers gives a model that compiles, with the same resolutions (`NamesConformanceTest`). clafer-vscode 0.6.0 runs it. `clafer-ls --version` prints its version and build date as the other tools do, `clafer-ls v0.6.0.2026-11-26` (the day of the build, or `-Dbuild.date`), and so does the server's `serverInfo`.
* `claferc`, the Clafer compiler's `clafer -m clafer` in Java (`org.clafer.frontend.ClaferCommand`, the `Main-Class` of the frontend's jar, installed as `claferc.jar` with the launcher `claferc`): the rich explicit model (`P.des.cfr`), with `--core` the explicit core model (`P.core.cfr`, with `--record-provenance` its provenance comments at the positions in the source's files), and with `--meta-data` the scope file and the map of names (`P.cfr-map`), with the compiler's statistics, warnings and errors. It takes `clafer`'s command line and forwards the other modes (`alloy`, the default, `choco`, `json`, `html`, `graph`, `cvlgraph`), the options it does not implement and the imports of URLs to `clafer` on the path. On clafer's 223 positive models, its outputs are the compiler's byte for byte (`ClaferCommandConformanceTest`).
* The command is `claferg`, the Clafer generator, for instance generation and optimization with Choco (and later Alloy): the launcher `solver/claferg`, which `make install` installs next to `chocosolver.jar`, with `chocosolver`, the old name, as a symlink to it. `--version` prints `claferg v0.6.0.<build date>`, and the usage errors name `claferg`. The jar is still `chocosolver.jar`, which `clafer --validate` reads from its `--tooldir`.
* `claferg` solves temporal models too, with Alloy 6.2.0 in the same JVM (the module `alloy/`, the artifact `clafer-alloy`), as claferIG does: one loop of solutions, an instance of a static model from Choco or a trace of a temporal model from Alloy (`org.clafer.ig.Repl`). `claferg --repl` on a temporal model is claferIG's REPL, with its commands, messages and traces, its unsat cores and near-misses, `check`, `fork`, `config`, `tl`, `b`, `a` and `c`; without `--repl`, claferg prints the traces, up to `-n`. On a static model, the REPL prints what it printed before, and it has claferIG's `d` (diff view), `e` (save), `f` (find), `dot` and `scope`. `z`, minimize, works also as `minimize`, and the help says minimi'z'e; `t` works, not only `stats`. A command of the other backend says so. The launcher passes the optimized MiniSat prover in `lib/`, if it is there.
* `claferc --version` prints the build date, as the other tools do: `claferc v0.6.0.2026-11-26`, from a `version.properties` that Maven fills in.
* The Java frontend reads the imports of URLs (`http`, `https`) and the web tools' restrictions of the imports, `--import-root`, `--public-imports` and `--import-base`, as the compiler does, with its messages (`ModelFiles.ImportOptions`, `Http`, on OkHttp 5.5.1, whose `Dns` gives it only the public address that was checked); the frontend's jar with its dependencies is `claferc.jar`, and the release bundle and the Docker images ship it with the launcher `claferc`; a model may be a URL too. chocosolver no longer falls back to the Haskell compiler for them. The language server still reads local files only.
* `transitiveClosure` and `transitiveReflexiveClosure` follow the relation more than one step ([#47](https://github.com/gsdlab/chocosolver/issues/47)). The search for the nodes that a node reaches started with the node's direct successors already marked as reached, so it never went past them: the domain of the closure had only the first step. With a relation that the model fixes, e.g., `N1.succ = N2`, `N2.succ = N3`, the closure was that first step, `N1.(succ.ref)^` was `N2` instead of `N2`, `N3`; otherwise the model had no instance that needs a longer path. `connected` uses the same closure. Test case `TransitiveTest.testChain`.

# chocosolver version 0.5.8, Nov 15, 2026

* Minor release with Clafer 0.5.8.
* The scope of an abstract clafer in a recursive hierarchy, e.g., `abstract Element` with `clip : Clip ?`, `abstract Group : Element` and `abstract Clip : Group`, could be computed before the scopes of its sub clafers, with the default scope for them, and be smaller than their scopes together: the solver crashed with an `ArrayIndexOutOfBoundsException` in `AstCompiler.initAbstract`, e.g., on the wiki model of the OMG Diagram Definition metamodel compiled with `clafer -k`. The scope analysis now computes each clafer of such a hierarchy after the clafers its scope depends on ([#48](https://github.com/gsdlab/chocosolver/issues/48)).
* A model that maps clafers one-to-one onto others, e.g., 28 bubbles onto 28 products with `[ all disj b1; b2 : Bubble | b1.prod != b2.prod ]`, got stuck ([#46](https://github.com/gsdlab/chocosolver/issues/46)), for two reasons:
  * `-n n` searched for one more instance after the n-th and dropped it. Up to symmetry, the bubbles have one instance, and proving that there is no other takes much longer than finding the first: `-n 1` printed the instance and then did not end. It now stops after the n-th instance, so `-n 1` ends in 0.4 s.
  * The default search, `PreferSmallerInstances` (Choco's failureRateBased since 0.5.3), broke its ties at random. Before any failure, all variables with the same domain size tie, so its first decisions were random, and on the wiki model ClaferTools/ClaferMooVizAbstractState they led into a subtree without instances: no instance after minutes, also with 5 products. The ties now go to the first variable, as in minDomLB (the default up to 0.5.2), and the model has an instance in 0.8 s. On Clafer's positive test models the first 10 instances and the Pareto fronts take the same time; enumerating all 100000 instances of `enforcingInverseReferences` takes more than 30 s (25 s before), and of `nested_quantifiers_with_membership` 26 s (24 s before). The measurements and the alternatives are in [benchmarking/search-strategy-0.5.8.md](benchmarking/search-strategy-0.5.8.md).
  * Proving that such a model has no other instance is still exponential: `-n 2` on the 28 bubbles does not end.
 `=`, `!=`, `in` and `not in` with a string reference joined over a set of more than one clafer, e.g., `[ "ada" in names ]` for `names -> string 2`, `[ A.ref = "abc" ]` for `A -> string 0..2`, or `[ A.ref in B.ref ]`, are compiled string by string, as their quantified forms, e.g., `some n : names | n = "ada"`. They were rejected with a `JoinSetWithStringException` ("Cannot join a non-singleton set with strings"), which is still the error for other uses of such a set, e.g., `length(A.ref)`. The wiki model `oclBench/b1` has instances ([#49](https://github.com/gsdlab/chocosolver/issues/49)).

# chocosolver version 0.5.7, Nov 8, 2026

* Minor release with Clafer 0.5.7.
* The names of clafers are their UIDs, which are their names since Clafer 0.5.7, qualified only where a name is not unique (`x__size`): the instances, also with `--prettify`, show them as they are. They cut a UID after its first `_` (`c0_size` was `size`, and `x__size` would have been `_size`).
* A name in a scope file or a REPL command is a UID or a qualified name with `__`, e.g., `Cfeatures` for all the clafers named so, `Component__Cfeatures` for those in a `Component`, and `root__Component__Cfeatures` for the one in a top-level `Component`; the older form `Component::Cfeatures` and `::Component::Cfeatures` is read too. The names are matched with the UIDs of the clafer and its ancestors, which no longer have a prefix to cut off.
* A join into a nested abstract clafer from a clafer that can be unused, e.g., `[ some this.parent.Task ]` under an optional child of `abstract System` with `abstract Task`, crashed with an `ArrayIndexOutOfBoundsException` when the abstract clafer's parent has several instances, e.g., two systems in one model.
* After the linear equation optimizer could not rewrite the equations of one model exactly, e.g., ones over integers up to 100000, it also kept the original equations of every later model in the same JVM, e.g., the REPL after a `reload`, alongside the rewritten ones. The result was the same but the models were larger. The flag was global and never reset; it now belongs to one optimization. Its tests failed depending on the order the test classes ran in.
* A wrong command line, i.e., an unknown option, an option without its argument or with a wrong one (e.g., `-n abc`, `--search Fastest`), no `--file` or an input file that does not exist, prints one line, e.g., `chocosolver: bogus is not a recognized option`, and a pointer to `--help`, and exits with 1. It ended with a Java stack trace, and a wrong argument only after compiling the model.
* The test classes run in parallel, in one JVM per core (`-Dtest.forks=1` for one at a time), with maven-surefire-plugin 3.6.0: `mvn package` takes half the time.
* A model that cannot be read, e.g., a `.js` file with a syntax error, exits with 1 after its error (`Unhandled compilation error occured`), also with `-v`: Clafer's `make test` validates its outputs so. It exited with 0.
* jopt-simple 5.0.4 (was 5.0.2), which parses the command line, and maven-assembly-plugin 3.8.0 (was 3.7.1), which builds the jar with dependencies. choco-solver 6.0.2 is already the latest release.
* Rhino 1.9.2 (was 1.9.1), which runs the JavaScript that Clafer generates, and SLF4J 2.0.20 (was slf4j-jdk14 1.7.21 from 2016, with slf4j-api 1.7.36), which passes the log messages of choco-solver's dependencies to `java.util.logging`.
* Explicit models are read directly, without the Clafer compiler: a `.cfr` file whose first line is `//# OPTIONS --explicit`, as `clafer -m clafer` writes it, or any `.cfr` file with `--explicit`, is read by `ExplicitParser`, with its scopes from its scope file (`model.des.cfr-scope` for `model.des.cfr`). Its errors are printed with their positions, e.g., `model.des.cfr:3:11: No clafer named y`, and chocosolver exits with 1. The REPL's `reload` reads it the same way, and `saveScopes` writes the scope file of any model name (it cut three characters off the name, i.e., the `.js`). For all 132 positive test models of Clafer with a Choco output, the explicit model and its scope file give the same instances as the `.js`. `AstPrinter.print` of a model with its objectives and assertions starts with that line.
  * The explicit model of a temporal model, which `clafer -m clafer` also writes, is refused with one error for each line with a temporal modifier or operator, e.g., `model.des.cfr:3:3: Chocosolver does not solve temporal models: initial is a temporal modifier; Alloy solves them (claferIG)`, in place of the errors that follow from them (`No clafer named X`).
* Java API, in preparation for a Clafer parser in Java:
  * The AST's expressions are records, and `AstExpr`, `AstSetExpr` and `AstBoolExpr` are sealed interfaces, so a pass over expressions is a `switch` that the compiler checks for a missing case. `AstExprVisitor` and `accept` are gone; `AstExprRewriter` dispatches with a `switch`, and its subclasses override the same `visit` methods as before. The accessors are the records' components, e.g., `join.left()` instead of `join.getLeft()`, `childRelation.childType()` instead of `getChildType()`, and `closure.reflexive()` instead of `isReflexive()`. Expressions are equal when their parts are, except locals (`AstLocal` stays a class), which are different variables even with the same name.
  * Source positions: `SourceSpan` (line and column, from 1, of the start and the end) on clafers (`clafer.at(span)`), constraints (`addConstraint(expr, span)`), assertions and objectives. A type error in a constraint, assertion or objective with a span starts with its position, e.g., `5:1: Cannot ...`, and the constraints of an unsat core or a Min-Unsat are printed with theirs, e.g., `[#(A) >= 1] at 2:5-2:14`. The JavaScript that Clafer generates has no positions yet, so the output is unchanged.
  * `AstPrinter` prints a model in a Clafer-like syntax with nothing implicit: UIDs, every card and group card as it applies, inherited ones too, `this`, `parent` and `dref`, and the objectives and assertions. Children, constraints and references are printed only where they are declared: in Clafer, a reference written on a sub clafer redefines the inherited one, even with the same target, so `ExplicitParser` takes a written reference as the clafer's own. An empty set, of any type, is printed as Clafer's `noclafer`, and parsed back as an empty set of the clafer of the set beside it (the other operand, or the other branch of an `if`), or of the model's first clafer. Nesting is in braces, `{}` for an empty clafer, so whitespace carries no meaning; the indentation is only for reading. The output is a Clafer model: `clafer -f -k -l --ss=none -m choco` compiles 129 of the 131 models to the same `.js` as the original's, up to the compiler's renaming of the UIDs (`c0_c0_A` for `c0_A`) in models with inheritance; strings stay Clafer literals, and a quantifier's names are separated by `;`, as in Clafer. The scopes are not in the model but in its `.cfr-scope` file.
  * `org.clafer.frontend.Lexer` splits this explicit form into tokens with their spans. Comments are set aside, and an error (an unexpected character, an unterminated string or comment, an unknown escape) is a diagnostic after which lexing goes on.
  * `org.clafer.frontend.ExplicitParser` reads the explicit form back into a model with its objectives and assertions, with the spans of the source, and reports errors as diagnostics and goes on. The round trip `.js` → model → explicit form → model prints the same and gives the same instances in the same order for all of Clafer's 131 positive test models with a Choco output; for the `.js` files that Clafer generated in 2015 (35 of chocosolver's 110 test models), which create all abstract clafers first, the instances are numbered differently. `AstPrinter` writes the abstract and concrete children of a clafer in the order of the source.
  * `org.clafer.scope.ScopeFile` reads and writes `.cfr-scope` files, which can now give every scope: besides `{"lpqName": name, "scope": n}`, the entries `{"defaultScope": n}`, `{"int": [low, high]}`, `{"mul": [low, high]}`, `{"stringLength": n}`, `{"chars": [low, high]}`, `{"decimalDigits": n}` and `{"decimal": [low, high]}`. `ScopeFile.print` writes all of them, every clafer by its UID, for the explicit form. On the command line, the file's scopes and ranges override the model's, and `--scope`, `--minint`, `--maxint` and `--decimal-digits` override the file's. A malformed file is an error that names the file and what is wrong, e.g., `model.cfr-scope: unknown entry "ints"`; files with only clafer scopes are read as before.
- `MainTest` runs the command line in a JVM of its own and checks its output and exit code: a wrong command line is one line and exits with 1, and so does a model that cannot be read, also with `-v`.

# chocosolver version 0.5.6, Nov 1, 2026

* `--addtypes`: with `--prettify`, each clafer of an instance is printed with its super clafer, e.g., `a1 : A -> e1`, as with `claferIG --addtypes`, in the normal, validation and REPL modes ([#43](https://github.com/gsdlab/chocosolver/issues/43)).
* Abstract clafers nested under concrete clafers, e.g., `abstract Port` under `System`, which Clafer compiles to `System.addAbstractChild("Port")` and chocosolver rejected with "Cannot find function addAbstractChild". As in claferIG, the concrete clafer is the parent of the abstract clafer's instances, and the instances are the same as claferIG's ([#23](https://github.com/gsdlab/chocosolver/issues/23)).
* Unsatisfiable models that crashed: a reference with no possible value, e.g., `x -> integer` with `[ x = 1 ]` and `[ x = 2 ]`, gave an `IllegalIntException` instead of no instances, and the `unsatCore` and `minUnsat` REPL commands gave an `UnsatisfiableException` when the cardinalities and scopes contradict each other without any constraint, e.g., `xor g` with `a 2` and `b 2`; they now say so.
* The instance of a clafer that redefines the reference of its super clafer, e.g., `a1 : A -> e1`, contains the children inherited from the super clafer; they were solved but not printed ([#42](https://github.com/gsdlab/chocosolver/issues/42)).

# chocosolver version 0.5.5, Oct 27, 2026

* Upgrade to choco-solver 6.0.2. The instances, Pareto fronts and the search of the default strategy are the same as with 4.10.18, and so are the times; `pickOnDom` and `conflictHistory` finish models that hit the time limit before.
* Java API: Choco's solver is final, so `ResetKeepsLimitsSolver` is replaced by `ResetKeepsLimits`. Time limits set with `ClaferSearch.limitTime` still hold across the restarts of the search; limits set on the Choco solver directly do not.
* Decimals: a primitive type `decimal` of numbers with a fixed number of fractional digits, the decimal scale of the model, solved as scaled integers, which Clafer 0.5.5 compiles to ([clafer#102](https://github.com/gsdlab/clafer/pull/102)). In the Javascript format: `refTo(Decimal)`, `decimal("19.99")`, `decimalScale(2)` and `decimalRange("-10", "10")`; on the command line, `--decimal-digits` overrides the scale. `decimal * decimal` and divisions with a decimal round half away from zero; a division of integers stays an integer division. The default range is the largest that fits Choco's integers, about ±214748.35 with 2 digits. Instances print decimals in their shortest form with at least one fractional digit, e.g. `199.0` and `12.5`. See [Decimals](README.md#decimals).
* Intervals of more than 65536 values are bounded domains in Choco instead of enumerated ones, and the products of such domains are no longer enumerated.
* Scope files: the CLI reads the scopes of clafers from the model's `.cfr-scope` file (`model.cfr-scope` next to `model.cfr` or `model.js`) if it exists, or from the file given by `--scope-file`, in all modes, and prints `Using the scopes from model.cfr-scope`. The file is a list of `{"lpqName": name, "scope": n}`, as `clafer --meta-data`, claferIG's and the REPL's `saveScopes` write it; a name is a UID or a (partially) qualified name, e.g., `Component::Cfeatures`, and a name that is not of a clafer in the model is an error. E.g., ClaferCaseStudies' `AADL_Complete.cfr-scope` makes its optimization 6 times faster with the same optimal instances. See [Getting started with the CLI](README.md#getting-started-with-the-cli).

# chocosolver version 0.5.4, Oct 25, 2026

* Models in several files: `--import=FILE` compiles the `.cfr` model together with the given file or URL, as the compiler's option does ([clafer#100](https://github.com/gsdlab/clafer/issues/100)); the files that the model imports in its `//# OPTIONS` directive are compiled with it too.
* Fixes: a constraint of an abstract clafer over its reference, when a sub clafer refines the reference to a subtype of the target (`abstract T -> Form`, `A : T -> Vector`), read the sub clafer's reference as another instance of the target, so a model could have no instances; `parent.parent` of an optional child of a nested abstract clafer with a larger scope than its parent crashed with an `ArrayIndexOutOfBoundsException` (also in the unsat core).
* With a `.cfr` model, the command line shows the compiler's errors when the model does not compile, or why there is no Choco output (e.g., temporal operators), instead of "File does not exist: model.js". It no longer uses a `.js` file left over from an earlier compilation, and file names may contain spaces.

# chocosolver version 0.5.3, Oct 15, 2026

* Upgrade to choco-solver 4.10.18.
* Time limits are a deadline for the whole search, including the restarts of optimization.
* The default search strategy is failureRateBased; a benchmark of the strategies is in `src/test/benchmark`.
* The command line uses the integer range of the model (`intRange`, from clafer's `--minint` and `--maxint`); `--minint` and `--maxint` still override it.

* `parent` of a top-level abstract clafer is the union of the parents of its subclafers ([clafer#84](https://github.com/gsdlab/clafer/issues/84)).
